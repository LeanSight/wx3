# wx41: Arquitectura Final del Pipeline Modular (Master Doc)

Fecha: 2026-03-02
Estado: Implementado y Verificado.

Este documento define la arquitectura final de `wx41`, basada en los aprendizajes de la reimplementación y el estándar idiomático Python 2026.

---

## 1. División Arquitectónica

El sistema se divide en dos capas principales para maximizar el desacoplamiento y la reutilización del motor:

### 1.1 Motor Genérico (`pipeline_engine.py`)
Contiene la lógica agnóstica de procesamiento secuencial. No tiene conocimiento de audio, video o transcripciones.
- **Pipeline**: Clase que ejecuta una lista de `NamedStep`.
- **NamedStep**: Abstracción de un paso que tiene un nombre, una función de ejecución (`fn`) y una función opcional de predicción de salida (`output_fn`).
- **PipelineObserver**: Protocolo para monitorear el progreso, inicio y fin de pasos sin acoplar la UI al motor.

### 1.2 Orquestación de Dominio (`wx4.py`)
Contiene el conocimiento específico de los flujos de trabajo de audio y video de `wx4`.
- **MediaOrchestrator**: Detecta el tipo de medio (MediaType) y despacha al pipeline correcto.
- **Builders**: `build_audio_pipeline` y `build_video_pipeline` definen la secuencia declarativa de pasos.

---

## 2. El Registro de Steps (`wx41/steps/`)

La fuente de verdad sobre las capacidades del sistema reside en el **Step Registry** (`steps/__init__.py`).

### 2.1 StepInfo (Metadata)
Cada paso se registra con un objeto `StepInfo` que centraliza:
- `config_class`: Dataclass que define los parámetros del paso.
- `step_fn`: La función de lógica del paso.
- `output_fn`: Función que predice qué archivos generará el paso.
- `optional`: Booleano para el generador de CLI.
- `description`: Ayuda para el usuario.

### 2.2 Auto-Descubrimiento (Discovery)
El sistema utiliza `pkgutil` para cargar dinámicamente cualquier módulo en `steps/`. Añadir un nuevo archivo `.py` en esa carpeta lo integra automáticamente en el sistema sin tocar el núcleo.

### 2.3 El Contrato: StepConfig Protocol
En `context.py`, se define el contrato que toda configuración debe cumplir:
```python
@runtime_checkable
class StepConfig(Protocol):
    enabled: bool
    output_keys: Tuple[str, ...]
```

## 3. Mecanismos Core

### 3.1 Resumability (Física)
`wx41` no utiliza archivos de estado JSON. La reanudación se basa en la realidad del disco:
1. El motor llama a `step.output_fn(ctx)`.
2. Si los archivos predichos existen, el motor actualiza `ctx.outputs` y salta la ejecución del paso.
3. El flag `--force` desactiva este chequeo.

**Ctrl+C**: Si el proceso se interrumpe, el motor detecta los archivos de salida predichos por el paso en ejecución y los borra automáticamente. No existe archivo de estado JSON.

### 3.2 Inyección de Dependencias (Partial)
El ensamblado utiliza `functools.partial` para inyectar los objetos `StepConfig` (específicos para cada paso) en las funciones genéricas de los pasos, manteniendo las firmas de las funciones limpias.

### 3.3 Path Oracle
La lógica de nombres de archivos se centraliza en `predict_output_path(src, step, key)`. Esto garantiza que los tests y la producción utilicen la misma convención de nombres basada en el archivo fuente original.

## 4. Flujos Declarativos

### 4.1 AudioPipeline
**Secuencia**: `normalize -> enhance -> transcribe -> srt -> black_video`

### 4.2 VideoPipeline
**Secuencia**: `normalize -> enhance -> transcribe -> srt -> compress`
*Mecanismo de "Mejor Audio"*: El paso `compress` integra automáticamente el audio de mayor calidad disponible (`enhanced > normalized > src`) durante el muxing.

---

## 5. Estrategia de Testing (Meta-AT)

Los tests de aceptación en `test_acceptance.py` son **Registry-Driven**:
- Utilizan `pytest.mark.parametrize` alimentado por `get_all_steps()`.
- Un "Simulador Universal" intercepta las llamadas a infraestructura.
- Garantiza que cualquier paso nuevo cumpla con el contrato de CLI, Resumability, Dry-run y Generación de archivos sin necesidad de escribir tests manuales adicionales.

---

## 6. Ventajas
- **Escalabilidad**: 100% plug-and-play.
- **Agnosticismo**: El motor es puro y no conoce el negocio.
- **Resiliencia**: Basado en contratos (Protocols) y verificación física de archivos.
